# DSH 创作套件项目计划

## 0. 项目代号

- 项目名：DSH Creative Suite
- 暂定包名：`@dsh-creative/suite`
- 形态：DSH 原生插件
- 目标模式：编码 / 酒馆 / MuseAI / Story

---

## 1. 项目目标

### 1.1 总目标

在一个 DSH 内融合：

- DSH 原生编码能力
- SillyTavern 酒馆能力
- MuseAI 创作页面
- Oh Story 四个创作工作台
- Story → MuseAI → Tavern → 反馈的内容飞轮

### 1.2 核心成功标准

1. 只安装一个 DSH 插件。
2. 不启动第二个 DSH。
3. 模型配置只有一套，全部走 DSH `ctx.llm`。
4. 四个模式可一键切换。
5. 人物卡、世界书、预设、文风、记忆可跨模式共享。
6. 小说可以蒸馏成剧本、世界书和人物卡。
7. 人物卡可以一键进入 Tavern 游玩。
8. Tavern 游玩结果可以回收成续写大纲和新角色。
9. 旧数据可迁移，更新不破坏本地资源。
10. 核心媒体生成有确认门、版本和任务记录。

### 1.3 非目标

第一阶段不做：

- 一次性重写整个 Tavern 兼容层
- 一次性重写全部 MuseAI 页面
- 把 Story / Tavern / MuseAI 的所有 UI 做成同一套组件
- 完全去掉 DSH 私有补丁，除非官方 API 已具备
- 支持所有 SillyTavern 第三方脚本

---

## 2. 关键原则

1. DSH 原生优先
2. 兼容层集中封装
3. 文件与数据可迁移
4. 模式按需接管
5. 媒体生产先确认
6. 单包、单安装、单更新

## 8. 主要风险与对策

| 风险 | 对策 |
|---|---|
| DSH 版本差异 | 锁定基线，做兼容矩阵，不盲目追新 |
| Session patch 失效 | 集中 compat 层，持续做回归 |
| 卡片生成质量差 | 草稿区、diff、人工确认、质量门槛 |
| 数据迁移复杂 | 先做只读迁移，再做写回 |
| UI 栈不统一 | 统一 slot / 主题层，逐步替换 |
| 媒体成本失控 | 预览 + 确认 + 任务记录 |
| 版权问题 | 只处理用户拥有/授权内容，保留来源 |
| 性能与体积 | 按需加载子模块 |
